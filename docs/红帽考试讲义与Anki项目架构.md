# 红帽考试讲义与 Anki 项目架构

## 1. 项目目标

本项目建设一套面向 RHEL 9 RHCSA 与 RHCE 的个人备考内容系统。系统的核心资产是：

```text
结构化讲义源
+
结构化 Anki 卡片源
+
稳定的构建与质量检查流程
```

它不是在线学习平台，不是知识库产品，也不是虚拟机考试平台。当前阶段优先保证：

- 内容准确；
- 讲义可连续阅读；
- 操作信息密度高；
- Anki 能深入训练命令、参数、输出和任务；
- Markdown、PDF、YAML 和 Anki 之间能够稳定更新；
- 项目复杂度保持可控。

---

## 2. 设计原则

### 2.1 单一内容真相

```text
讲义 Markdown 是讲义内容真相
Anki YAML 是卡片内容真相
```

PDF、HTML 预览、Anki Note 和 `.apkg` 都是构建产物，不手工维护。

### 2.2 单向构建

```text
Markdown → HTML → PDF
YAML → 校验 → HTML 预览 → AnkiConnect
```

不从 PDF 反向抽取讲义，不从 Anki 反向覆盖 YAML，不建设复杂双向同步。

### 2.3 稳定 ID

章节、专题、操作专题、经典任务和 Anki Note 使用稳定 ID。ID 属于维护层，在正式 PDF 和卡片界面中隐藏。

稳定 ID 支持：

- 讲义与卡片关联；
- 更新与去重；
- 覆盖检查；
- AnkiConnect 增量更新；
- 内部链接；
- 问题定位。

### 2.4 无虚拟机依赖

Codex 必须假设始终无法访问虚拟机。项目通过课程材料、官方文档、静态语法检查和操作逻辑推演保证质量。

当前不建设：

- 虚拟机拓扑；
- 快照；
- 自动评分；
- 初始化脚本；
- 重置脚本；
- 实验执行记录。

这些能力未来可以在独立子项目中扩展，不能反向增加当前讲义与 Anki 的复杂度。

### 2.5 用户控制同步

生成章节后先交付 PDF 和 Anki HTML 预览。只有用户明确要求同步时，才调用 AnkiConnect。生成完成不等于已经进入正式牌组。

## 5. 内容源结构

### 5.1 章节 Markdown

每章一个主 Markdown 文件。文件包含：

```text
隐藏 Front Matter
章标题与引入
章首概念与操作语义
若干知识专题
若干操作专题
必要的诊断专题
经典任务
参考解答
本章收束
```

专题使用隐藏 HTML 属性关联稳定 ID：

```html
<section
  id="RHCSA-LVM-O03"
  class="topic operation"
  data-kind="operation-topic">
```

正式渲染只显示自然标题和 `[操作专题]` 类型标记。

### 5.2 章节 Anki YAML

每章一个 YAML 文件，包含 `RedHat-QA` 与 `RedHat-Cloze` 条目。

Markdown 与 YAML 分开维护，但共享：

- chapter ID；
- topic ID；
- operation ID；
- classic task ID。

不把 Anki 标记嵌入讲义，不从 PDF 中抽卡。

### 5.3 是否需要 manifest

默认不要求每章维护复杂 manifest。只有当后续构建脚本确实需要统一入口时，才增加一个极简 `chapter.yml`：

```yaml
chapter_id: RHCSA-LVM
lecture: lecture.md
anki: anki.yml
```

不能把 manifest 扩展成大型知识管理模型。

## 6. 讲义构建架构

固定链路：

```text
lecture.md
→ Markdown 解析
→ 规范化 HTML
→ lecture.html 模板
→ lecture.css
→ 固定 HTML/CSS PDF 渲染器
→ PDF
```

构建层负责：

- 目录和 PDF 书签；
- 章节分页；
- 经典任务题解分页；
- 隐藏 ID 锚点；
- 代码块和行末注释样式；
- 深蓝色专题类型标记；
- `①②③` 内部点标题；
- Cheatsheet 样式；
- 页码；
- A4 纵向版式。

构建层不负责改变内容含义，也不能自动重写命令。

所有章节共用一套模板和 CSS。样式变更先在基准样章验证，再全局应用。

---

## 7. Anki 构建架构

固定链路：

```text
anki.yml
→ YAML 解析
→ Schema 检查
→ ID 与重复检查
→ 覆盖检查
→ Markdown 转安全 HTML
→ 静态预览
→ 用户查看
→ AnkiConnect 增量同步
```

### 7.1 Note Type

只保留：

```text
RedHat-QA
RedHat-Cloze
```

卡片类型通过标签表达，不新增大量模板。

### 7.2 AnkiConnect

AnkiConnect 是日常同步入口。同步脚本负责：

- 检查连接；
- 创建或确认 Note Type；
- 按稳定 ID 查找 Note；
- 新增或更新字段；
- 更新标签；
- 同步必要媒体；
- `disabled: true` 时暂停；
- 输出新增、更新、暂停和失败数量。

同步脚本不负责：

- 修改学习步长；
- 修改每日新卡数量；
- 修改 FSRS 参数；
- 从 Anki 反向覆盖 YAML；
- 自动删除 Note；
- 未经用户指令自动推送。

### 7.3 阶段性 `.apkg`

完成 RHCSA、RHCE 或整套牌组后生成 `.apkg`，用于：

- 备份；
- 迁移；
- 独立导入；
- 发布。

不为每章都生成 `.apkg`。

## 8. 质量检查架构

### 8.1 讲义检查

自动或半自动检查：

- 章节是否包含章首概念与操作语义；
- 专题标题是否标注类型；
- 专题 ID 是否唯一；
- 是否存在过多碎片标题；
- 操作专题是否包含操作与验证；
- 新命令是否在使用前解释语义；
- 关键参数是否有介绍；
- Cheatsheet 是否只引用已出现内容；
- 经典任务是否有任务页和参考解答；
- 是否存在可见版本说明、来源和 ID；
- 代码块是否正常闭合；
- HTML 结构是否完整。

以下仍需由 Codex 内容判断：

- 专题是否真正内聚；
- 自然语言是否只承担理解与连接；
- 场景是否牺牲了信息密度；
- 行末注释是否简短并切中对象变化；
- 验证是否真的对应目标状态；
- 内容是否把静态推断写成实测结论。

### 8.2 Anki 检查

硬性检查：

- YAML 可解析；
- ID 唯一；
- QA 题面与答案存在；
- Cloze 合法；
- 卡片标签包含考试、章节和类型；
- 无法确认的高风险结论未进入精确卡；
- `disabled` 卡不计入有效覆盖。

覆盖检查：

- 知识专题；
- 操作专题；
- 参数；
- 验证；
- 诊断；
- 经典任务；
- 讲义外高价值命令和参数。

非阻断提醒：

- 某专题卡片密度异常；
- 补充说明偏长；
- 近似重复；
- Cloze 比例偏高；
- 缺少某个可能有价值的提取角度。

## 9. 章节生产流程

```text
1. 从知识树选择章节
2. 建立官方课程与模拟题来源映射
3. 确定章首概念、主要专题和经典任务
4. 编写讲义 Markdown
5. 检查专题内聚性与命令引入
6. 编写 Anki YAML
7. 运行讲义与 Anki 静态检查
8. 生成 PDF、Anki HTML 预览和覆盖摘要
9. 用户查看并反馈
10. 修改内容和全局规范
11. 用户明确要求后通过 AnkiConnect 同步
12. 章节冻结为后续章节参考
```

每完成一个章节，讲义和 Anki 同时交付。不能先批量写完讲义，再在最后补整套卡片。

## 10. 基准样章与模板冻结

基准样章的作用是固定：

- 讲义叙事深度；
- 专题内聚性；
- 章首概念与操作语义；
- `①②③` 点式组织；
- 命令前参数说明；
- 对齐的行末注释；
- 专题 Cheatsheet；
- Anki 的“极客”程度；
- PDF 和 Anki 视觉模板。

当前最重要的经验来自 LVM 高密度操作版：

1. 自然语言不等于长篇连续叙述；
2. 专题内部需要明确呈现知识点和操作点；
3. 场景只服务理解，不能压低信息密度；
4. 新命令必须说明作用对象和关键参数；
5. 代码中的关键行应有短而对齐的注释；
6. Anki 要比讲义更深入地覆盖命令、参数和典型任务；
7. 专题末 Cheatsheet 能把展开知识压缩成可调用骨架；
8. 专题必须独立成立，不能依赖“接着上文”。

后续章节使用同一方法，但不能机械复制 LVM 的篇幅和点数量。

## 11. 角色分工

### 用户

- 确定考试版本和学习目标；
- 审阅 PDF 与 Anki 预览的整体效果；
- 决定是否冻结模板；
- 明确发出 Anki 同步指令；
- 决定章节优先级和学习顺序。

### Codex

- 读取资料并建立来源映射；
- 编写讲义和 Anki；
- 完成静态核对；
- 执行构建和质量检查；
- 生成 PDF、HTML 预览和摘要；
- 根据反馈统一修改规范和样章；
- 在收到指令后调用 AnkiConnect。

Codex 不声称进行过真实虚拟机实测。

## 12. 复杂度控制

项目明确不做：

- 数据库；
- Web 后台；
- 多用户；
- 在线同步服务；
- Anki 双向编辑；
- 自动生成大量 Note Type；
- 每章独立 CSS；
- 逐句知识映射；
- 复杂审核工作流；
- 多级卡片生命周期；
- 自动同步到 Anki；
- 虚拟机评分平台。

引入新组件前必须回答：

1. 它是否直接提高讲义质量、Anki 质量或同步可靠性？
2. 能否用现有 Markdown、YAML 和脚本完成？
3. 它是否要求用户承担新的维护动作？
4. 它是否会把内容项目变成软件平台项目？

无法明确产生价值时，不引入。

## 13. 交付物

### 单章交付

```text
章节 PDF
Anki 静态 HTML 预览
```

项目内部同时保留：

```text
lecture.md
anki.yml
覆盖摘要
构建报告
```

### 阶段性交付

```text
RHCSA PDF
RHCE PDF
合订版 PDF
RHCSA .apkg
RHCE .apkg
项目源文件与规范
```

### 章节完成定义

```text
讲义完成
+
Anki 完成
+
静态检查通过
+
PDF 与预览生成成功
+
用户完成整体查看
```

Anki 是否已同步属于发布状态，不属于内容完成条件。

## 14. 最小可用工具集

项目初期只需要：

```text
Markdown 解析器
HTML/CSS PDF 渲染器
YAML 解析器
Markdown→HTML 转换与清理
AnkiConnect 客户端
少量 Python 构建脚本
```

工具选择确定后固定版本和调用方式，不在不同章节中更换构建路线。

项目的核心始终是高质量内容，而不是工具本身。
