# 红帽 RHCSA / RHCE Anki 制卡规范（高密度背景化版）

## 0. 文档定位

本文档用于统一约束 RHEL 9 RHCSA / RHCE 讲义配套 Anki 的内容范围、题面背景、卡片深度、卡片家族、字段结构、稳定 ID、标签、预览、覆盖检查与同步方式。

它替代此前偏“章节摘要式”“每章固定数量式”的制卡方法。

本规范的核心目标不是生成更多卡片，而是让每一个重要知识点和操作点都能从多个真实、可判定、可迁移的角度被主动提取。

Anki 的定位是：

> 把已经在讲义中理解过的系统对象、命令、参数、输出、验证和诊断，转化为可在考试和真实运维中快速调用的记忆。

Anki 不负责第一次讲懂复杂机制，也不能成为讲义遗漏内容的补丁区。讲义必须自包含；Anki 负责更高频、更精确、更“极客”的提取训练。

---

# 第一部分　总体原则

## 1. Anki 训练的不是“记住一句话”，而是建立调用路径

每个高价值内容应尽量训练以下调用方向中的若干个：

```text
任务目的
→ 选择对象
→ 选择命令或模块
→ 选择关键参数
→ 执行典型操作
→ 解读输出
→ 判断当前状态
→ 区分持久状态
→ 选择下一条证据
→ 完成分层验证
→ 识别安全边界
```

例如 LVM 扩容不能只做一张：

> 扩容 LV 用什么命令？

而应根据价值形成一个卡片家族：

```text
目标 → `lvextend`
参数 → `-l` / `-L` / `+`
任务 → 增加 20 LE 的命令
联动 → `-r` 是否同步扩展文件系统
输出 → `lvs` 已增大而 `df` 未变化
验证 → `lvs`、`df`、`findmnt`
边界 → VG 余量不足时下一步
```

卡片深度来自多角度提取，而不是把一张卡答案写得很长。

---

## 2. “极客型卡片”是默认方向

优先制作：

- 命令骨架；
- 参数语义；
- 参数组合；
- 命令作用对象；
- 配置文件路径；
- 配置字段；
- 真实输出判断；
- 当前状态与持久状态；
- 功能验证；
- 诊断下一步；
- 安全边界；
- 命令帮助入口；
- RHCE 模块名、字段、YAML 骨架和幂等性；
- 工作中常见的真实变式。

谨慎制作：

- 长篇概念定义；
- 历史背景；
- 章节总结；
- 泛泛的“请解释”；
- 没有唯一判断边界的开放题；
- 只靠重新阅读讲义才能回答的题；
- 纯记忆口号；
- 仅为达到卡片数量而生成的改写卡。

不推荐：

```text
题面：请介绍 systemd。
答案：一大段 systemd unit、service、target、依赖和状态说明。
```

推荐拆成：

```text
题面：systemd unit 的 `ActiveState` 与 `UnitFileState` 分别回答什么问题？
题面：`Requires=` 与 `After=` 的区别是什么？
题面：管理员覆盖 vendor unit 时，为什么优先使用 drop-in？
题面：`systemctl daemon-reload` 与应用 reload 的区别是什么？
```

---

## 3. 卡片数量由知识树决定，不按章节配额生成

禁止采用：

```text
每章 12 张 QA + 2 张 Cloze
每个专题固定 10 张
每章强制 20 张
```

真实章节密度不同：

- Shell 引用与展开可能需要 40～70 个 Note；
- systemd 可能需要 80～150 个 Note；
- LVM 可能需要 70～120 个 Note；
- 综合任务可能主要是流程、判断和诊断卡，不需要和 systemd 数量相同。

卡片数量应由以下内容自然生长：

```text
知识点数量
操作点数量
关键参数数量
输出判断数量
验证层次
诊断路径
典型任务变式
安全边界
```

# 第二部分　题面背景与范围

## 4. 为什么题面需要适量背景

没有背景的题面容易出现：

- 对象不明确；
- 当前状态不明确；
- 多种答案都合理；
- 无法判断题目考命令、参数、验证还是诊断；
- 题面像从讲义截出的标题；
- 复习时缺乏真实调用感。

例如：

```text
`active` 与 `enabled` 的区别是什么？
```

本身并非错误，但略抽象。

改进后：

```text
查看一个 systemd service 时，`active` 与 `enabled` 分别说明哪个状态维度？
```

再进一步：

```text
某服务当前为 `active`，题目还要求系统重启后自动启动。还必须检查什么状态？
```

第二种更接近真实判断，但仍只有一个提取目标。

---

## 5. 题面背景只补足必要信息

背景通常只需补足以下四类信息中的一到两类：

```text
对象是谁
当前已知什么
目标是什么
哪些范围已经排除
```

题面背景不承担完整教学职责。

不应把题面写成：

- 半页任务描述；
- 把所有答案提示都列出来；
- 复述整段讲义；
- 同时考多个独立目标；
- 要求读者先阅读大量上下文才能作答。

判断标准：

> 背景应让答案唯一、范围清楚，但不能替代答案本身。

---

## 6. 三种背景等级

### 6.1 轻量背景

结构：

```text
对象 + 操作目标
```

适合：

- 命令卡；
- 参数卡；
- 语法卡；
- 短输出判断卡；
- 精确路径卡。

示例：

原题：

> 向 PID 2450 请求有序退出并检查是否仍存在，命令是什么？

改进：

> 你已经确认 PID 2450 是目标进程。怎样先请求它有序退出，再检查它是否仍存在？

特点：

- 只增加必要范围；
- 不增加复杂场景；
- 保留高频提取速度。

---

### 6.2 中等背景

结构：

```text
对象 + 当前状态 + 操作目标 + 一个关键范围
```

适合：

- 验证卡；
- 输出判断卡；
- 诊断卡；
- 命令选择卡；
- 当前/持久状态卡；
- 容易存在多个合理答案的卡。

示例：

> `chronyd.service` 为 `active`，但指定时间源在 `chronyc sources -v` 中持续显示 `^?`，本机也未进入有效跟踪状态。下一步应按什么链路调查？

这里明确：

- 服务已经运行；
- 故障对象是时间源；
- 目标是诊断链路；
- 不需要回答“先启动 chronyd”。

中等背景是默认推荐程度。

---

### 6.3 较完整背景

结构：

```text
场景 + 已知证据 + 关键约束 + 目标
```

适合：

- 流程卡；
- 综合任务卡；
- 多层诊断卡；
- 安全边界卡；
- 经典任务变式；
- 工作迁移卡。

示例：

> 系统中存在多个同名 worker。你已经通过用户、启动时间和完整命令行确认 PID 2450 是旧实例，并确认它不属于任何 systemd service。要求优先有序终止，等待两秒后检查是否仍存在。应执行哪些命令？

这种题面可以训练完整操作，但不适合所有普通卡。

---

## 7. 不同卡片类型的默认背景等级

| 卡片类型 | 默认背景 |
|---|---|
| 命令骨架 | 轻量 |
| 参数语义 | 轻量 |
| 路径/模块名 | 轻量 |
| 语法结构 | 轻量 |
| 输出判断 | 中等 |
| 验证边界 | 中等 |
| 命令选择 | 中等 |
| 诊断下一步 | 中等 |
| 当前/持久区别 | 中等 |
| 经典任务 | 较完整 |
| 流程骨架 | 较完整 |
| 安全边界 | 中等或较完整 |
| 综合验收 | 较完整 |

---

## 8. 题面背景的自检

每张卡检查：

- 是否说明了操作对象？
- 是否提供了决定答案所需的当前状态？
- 是否明确要求提取命令、参数、判断、验证还是下一步证据？
- 是否排除了最重要的歧义？
- 是否泄露了答案？
- 是否包含了与提取目标无关的背景？
- 是否可以再缩短而不损失唯一性？

# 第三部分　卡片原子性

## 9. 一张卡只训练一个主要提取目标

一个主要提取目标可以是：

- 一个命令骨架；
- 一个参数区别；
- 一个输出状态；
- 一个验证边界；
- 一个诊断下一步；
- 一个流程骨架；
- 一组不可拆分的固定字段。

不合格：

> 如何创建 systemd service、启用、启动、查看日志并验证端口？

这同时训练五个独立目标。

推荐拆为：

1. 自定义 service 的基本 unit 骨架；
2. unit 变化后需要执行什么；
3. 当前启动与开机启用如何分别表达；
4. 怎样查询该 unit 日志；
5. 怎样证明应用实际监听。

---

## 10. 原子性不等于题面必须很短

题面可以有中等背景，但答案仍只应有一个核心。

例如：

> `httpd.service` 当前是 `active`，但题目还要求重启后自动启动。还应查询什么？

核心答案只有：

```bash
systemctl is-enabled httpd.service
```

题面虽然有背景，但并没有增加第二个提取目标。

---

## 11. 流程卡的特殊规则

流程卡可以包含多个阶段，但只训练“顺序和依赖”，不要求同时背全部命令。

例如：

> 为一个新 LV 建立可持久挂载的 XFS，主要阶段顺序是什么？

答案：

```text
确认设备
→ PV
→ VG
→ LV
→ 文件系统
→ 挂载点
→ fstab
→ 当前挂载与持久性验证
```

每个具体命令另做原子卡。

# 第四部分　卡片家族

## 12. 一个高价值操作应考虑哪些卡片方向

不是每个操作都必须机械生成全部类型，但 P0 操作通常不能只有一张卡。

推荐矩阵：

| 方向 | 提取目标 |
|---|---|
| 对象 | 命令直接作用于什么 |
| 语义 | 命令本质查询或改变什么 |
| 选择 | 某目标应使用哪个命令/模块 |
| 骨架 | 基本命令或 YAML 结构 |
| 参数 | 关键参数的准确语义 |
| 组合 | 高频参数组合 |
| 任务 | 给定具体目标写出命令 |
| 输出 | 根据真实字段判断状态 |
| 验证 | 操作后看什么 |
| 边界 | 什么不能由该证据证明 |
| 诊断 | 失败后下一条证据 |
| 安全 | 破坏性或误操作风险 |
| 帮助 | 不确定时如何查询 |

---

## 13. 示例：SIGTERM 操作卡片家族

### 对象卡

> 对一个已经确认的 PID，`kill` 直接作用于什么对象？

答案：

> 当前进程实例或进程组，不负责按名称查找。

### 语义卡

> `SIGTERM` 与 `SIGKILL` 的本质区别是什么？

### 命令卡

> 你已确认 PID 2450 是目标进程，且不由 systemd 管理。怎样请求有序退出并检查它是否仍存在？

### 参数卡

> `kill -0 PID` 做什么？

### 诊断卡

> 对 PID 发送 TERM 后它很快以新 PID 出现，应优先调查什么？

### 边界卡

> 为什么不应默认从 `kill -9` 开始？

---

## 14. 示例：systemd 服务管理卡片家族

### 状态卡

> 查看 systemd service 时，`active` 与 `enabled` 分别说明哪个状态维度？

### 命令卡

> `chronyd.service` 当前未运行，题目要求现在启动并在重启后自动启动。命令是什么？

```bash
systemctl enable --now chronyd.service
```

### 验证卡

> 执行 `enable --now` 后，为什么仍应分别运行 `is-active` 和 `is-enabled`？

### 参数/行为卡

> `disable` 与 `mask` 的强度区别是什么？

### 配置卡

> 管理员覆盖 vendor unit 时，为什么优先使用 `systemctl edit` 创建 drop-in？

### 诊断卡

> `cups.service` 停止后又被拉起，应优先查询哪些触发入口？

---

## 15. 示例：Journal 卡片家族

### 命令卡

> 服务器刚重启，需要调查上一轮启动中的错误。怎样列出可用 boot，并查看上一次启动中 `err` 及更严重的日志？

### 参数卡

> `journalctl -b -1` 中 `-1` 表示什么？

### 输出卡

> `journalctl --list-boots` 中没有上一轮记录，能否证明上次没有错误？

### 边界卡

> 为什么第一轮调查不宜直接使用 `-p err` 过滤全部上下文？

### 持久性卡

> 怎样真正证明 journal 已跨重启保存？

---

## 16. 示例：cron 卡片家族

### 结构卡

> 将用户 crontab 任务迁移到 `/etc/cron.d/*` 时，字段结构需要增加什么？

### 语法卡

> 用户 crontab 的五个时间字段顺序是什么？

### 参数/符号卡

> cron 命令字段中的未转义 `%` 有什么特殊含义？

### 环境卡

> 脚本手工成功但 cron 失败时，为什么应使用 `env -i` 模拟最小环境？

### 任务卡

> 给 `monitor` 用户配置每天 02:15 执行的健康检查，系统级 cron 条目如何写？

### 验证卡

> crontab 中存在条目，为什么仍不能证明任务成功？

# 第五部分　题面写法

## 17. 推荐题面句式

### 命令卡

```text
你已确认……，现在希望……。应执行什么命令？
```

### 参数卡

```text
在……命令中，`-x` 与 `-y` 分别改变什么？
```

### 输出卡

```text
已知……，输出显示……。最合理的判断是什么？
```

### 验证卡

```text
已经完成……，还需要检查什么，才能证明……？
```

### 诊断卡

```text
已确认……，但出现……。下一条最有区分度的证据是什么？
```

### 边界卡

```text
为什么仅凭……不能证明……？
```

### 流程卡

```text
在……约束下，主要阶段应按什么顺序完成？
```

---

## 18. 不推荐题面

### 太抽象

```text
如何验证？
```

### 太开放

```text
请全面介绍 chrony。
```

### 多目标混杂

```text
如何配置、启动、调试并持久化一个服务？
```

### 泄露答案

```text
chronyd active 但源 `^?`，请从 DNS、UDP 123、远端响应和样本积累进行排查。
```

这里已经把答案层次列出。

更好：

```text
chronyd 为 active，但指定源持续显示 `^?`。下一步应按什么链路排查？
```

# 第六部分　答案结构

## 19. 背面结构

背面只显示：

```text
最低合格答案

必要补充
```

不显示：

- 题面重复；
- 章节；
- 稳定 ID；
- 来源；
- 标签；
- 优先级；
- 卡片类型徽标。

---

## 20. 最低合格答案

答案必须：

- 一眼可判断对错；
- 足够精确；
- 尽量短；
- 保持真实命令和语法；
- 不把所有变体一起罗列。

示例：

题面：

> `lvs` 已显示 LV 增长，但 `df -hT` 仍显示旧容量。优先判断哪一层未完成？

最低答案：

> 文件系统层未扩展。

补充：

> `lvs` 只证明 LV 层容量；还需扩展文件系统并再次检查 `df`。

---

## 21. 答案中的代码

命令和配置应保持真实格式。

短命令：

```bash
systemctl is-enabled httpd.service
```

多行命令：

```bash
systemctl show httpd.service \
  -p LoadState,ActiveState,SubState,UnitFileState
```

配置骨架：

```ini
[Service]
Type=exec
ExecStart=/usr/local/bin/app
Restart=on-failure
```

YAML：

```yaml
- name: Start and enable httpd
  ansible.builtin.systemd_service:
    name: httpd
    state: started
    enabled: true
```

不要把多行代码压成一行字符串。

---

## 22. 补充说明的长度

补充说明通常：

- 一至三句；
- 或一个短代码块；
- 或三项以内的短列表。

超过一个短段落时，应考虑：

- 拆卡；
- 缩小题面；
- 把解释交回讲义。

---

# 第七部分　命令、参数与配置卡

## 23. 命令骨架卡

使用占位符训练可迁移结构：

```bash
kill -TERM <PID>
lvextend -l +<LE_COUNT> -r <VG>/<LV>
journalctl -u <UNIT> -b --since '<TIME>'
```

占位符统一使用：

```text
<PID>
<UNIT>
<USER>
<PATH>
<VG>
<LV>
<PORT>
<DEVICE>
```

---

## 24. 具体任务卡

只有具体值能暴露真实易错点时才创建。

值得创建：

- `+20` 与 `20`；
- PE/LE 数量；
- 端口方向；
- cron 字段顺序；
- SELinux 类型；
- systemd unit 名称；
- YAML 缩进；
- 引号和转义；
- UUID 与路径；
- 用户与执行身份。

不值得创建：

- 只把 `alice` 换成 `bob`；
- 只把端口 8080 换成 8081；
- 不增加任何新判断的同义实例。

---

## 25. 参数卡

优先覆盖：

- 目标值与增量值；
- 替换与追加；
- 当前与持久；
- 精确与模糊匹配；
- 作用范围；
- 默认值；
- 破坏性；
- 正负号；
- 大小写；
- 百分比；
- 是否自动联动。

例如：

```text
`lvextend -l 20` 与 `lvextend -l +20` 的区别？
```

```text
`pgrep -x` 与 `pgrep -f` 的区别？
```

```text
`firewall-cmd --add-port` 与加 `--permanent` 的差异？
```

## 26. 配置骨架卡

适合制作骨架卡的内容：

- `/etc/fstab`；
- `/etc/cron.d/*`；
- sudoers；
- systemd unit；
- systemd timer；
- rsyslog selector/action；
- logrotate；
- autofs map；
- NetworkManager 命令；
- Ansible Task；
- Jinja2；
- Role 目录。

配置骨架卡应只挖或提取关键结构，不要求输入完整长文件。

# 第八部分　输出、验证与诊断卡

## 27. 输出卡

输出卡题面只保留稳定、必要字段。

推荐：

```text
`ps` 中目标进程状态为 `D`，CPU 使用率不高，但 load average 持续升高。最合理的下一步是什么？
```

不推荐：

- 大段完整日志；
- 随机 PID；
- 时间戳；
- UUID；
- 与判断无关的几十行输出。

---

## 28. 验证卡

每个重要操作至少要考虑：

- 当前状态；
- 持久状态；
- 功能状态；
- 外部访问；
- 数据状态；
- 幂等性。

例如 systemd 服务：

```text
is-active
is-enabled
journalctl -u
ss
curl
```

卡片应训练：

- 各自证明什么；
- 不能证明什么；
- 还缺哪一层。

---

## 29. 诊断卡

诊断卡默认使用中等背景。

结构：

```text
已知证据
→ 具体现象
→ 下一条最有区分度的证据
```

推荐：

> `httpd.service` 为 active，但本机 `curl` 失败。下一步最先检查什么？

答案不应直接是十项排查大全，而应给出最有价值的下一步：

> 先确认实际监听地址和端口：`ss -lntp`。

后续另做：

- 有监听但本机 curl 失败；
- 本机成功但远端失败；
- 远端 TCP 通但 HTTP 返回错误。

这样形成证据推进链。

# 第九部分　QA 与 Cloze

## 30. Note Type

只保留：

```text
RedHat-QA
RedHat-Cloze
```

不为 command、diagnosis、parameter 等建立独立 Note Type。

这些类型通过标签表达。

---

## 31. QA

QA 是主要形式，适合：

- 命令选择；
- 参数语义；
- 输出判断；
- 验证；
- 诊断；
- 流程；
- 比较；
- 配置骨架。

一条 QA YAML 生成一张卡。

---

## 32. Cloze

Cloze 只用于精确结构：

- 正负号；
- 参数位置；
- 大小写；
- 固定字段；
- 短配置结构；
- 命令中容易遗漏的部分。

推荐：

```text
`lvextend -l {{c1::+20}} {{c2::-r}} projectvg/projectlv`
```

不推荐：

- 对整段 Playbook 挖十几个空；
- 将普通概念句重复制作成 Cloze；
- 与 QA 完全相同的提取目标；
- 长篇文字挖空。

一个 Cloze Note 通常：

- 1 个编号；
- 最多 2 个紧密相关编号。

# 第十部分　YAML 数据结构

## 33. 每章一个 YAML

推荐：

```yaml
chapter_id: RHCSA-SYSTEMD
deck: RedHat::RHCSA-RHEL9

notes:
  - id: RHCSA-SYSTEMD-O02-QA-001
    type: qa
    question: >-
      `httpd.service` 当前为 active，题目还要求系统重启后自动启动。
      还必须检查什么状态？
    answer: |-
      ```bash
      systemctl is-enabled httpd.service
      ```
    extra: >-
      `active` 证明当前运行；`enabled` 证明持久启动配置。

      - systemctl(1)
      - systemd.unit(5)
    tags:
      - exam::rhcsa
      - chapter::systemd-units-services
      - card::verification
      - priority::P0
```

QA：

```text

type

answer
extra
source
tags
disabled（可选）
```

Cloze：

```text

type
text
extra
source
tags
disabled（可选）
```

## 35. Source 字段必须保留

Source 不显示在卡片正反面，但必须存入 Note。

来源可包括：

```text

RH294

Ansible 官方文档
模拟题
```

作用：

- 审计；
- 版本更新；
- 冲突回溯；
- 判断版本敏感；
- 修复错误；
- 区分课程要求和工作扩展。

# 第十一部分　稳定 ID

## 36. ID 代表提取目标

示例：

```text
RHCSA-SYSTEMD-O02-QA-001
RHCSA-PROCESS-D01-QA-003
RHCE-TEMPLATE-O04-CLOZE-002
```

推荐组成：

```text
考试
章节
专题/操作/诊断
Note 类型
顺序
```

---

## 37. 保留 ID 的情况

- 修改题面背景；
- 精炼答案；
- 修正错别字；
- 调整补充说明；
- 增加来源；
- 更新标签；
- 同一提取目标下优化代码格式。

本轮“增加一点背景和范围”通常保留原 ID。

---

## 38. 创建新 ID 的情况

- 主要提取方向改变；
- 从命令卡变为诊断卡；
- 一张宽卡拆成多张；
- 核心正确答案变化；
- RHCSA 手工操作变为 RHCE 自动化表达；
- 从抽象比较变为新的具体任务。

---

## 39. 停用

不再使用的卡：

```yaml
disabled: true
```

同步时暂停，不自动删除。

## 42. 优先级定义

### P0

不掌握会阻断核心考试任务：

- 核心命令；
- 核心参数；
- 当前/持久区别；
- 基本验证；
- 高风险安全边界；
- 核心诊断入口。

### P1

高频变式、常见工作场景、深入参数与典型诊断。

### P2

较低频但有工作价值的扩展、识别性内容和帮助入口。

禁止把 80% 以上卡片全部标成 P0。

# 第十三部分　重复与去重

## 43. 多角度提取不等于重复

以下可以同时存在：

```text
目的 → 命令
命令 → 参数
输出 → 判断
失败 → 下一步
操作 → 验证
```

它们训练不同路径。

---

## 44. 实质重复

以下通常属于重复：

- 同一具体命令，只替换无意义数字；
- 两张题面不同但答案和提取目标完全相同；
- QA 与 Cloze 训练完全相同内容；
- 同一知识点在多个章节重复制作；
- 方法论口号用不同措辞重复。

处理原则：

- 保留一个主归属 Note；
- 添加多个相关标签；
- 相关章节只引用；
- 只有提取方向不同才建新卡。

## 46. RHCE 负责自动化表达

训练：

## 48. HTML 预览要求

预览应支持：

- 按专题筛选；
- 按卡片类型筛选；

- 覆盖数量统计。

维护元数据只用于预览，不进入正式卡片界面。

## 49. 覆盖摘要

至少统计：

- Note 总数；
- QA/Cloze；
- 各章节；
- 各专题；
- 各类型；
- P0/P1/P2；
- `coverage::extra`；
- 多行代码卡；
- 输出卡；
- 参数卡；
- 诊断卡；
- 经典任务卡；
- 缺少 Source；
- 重复 ID；
- 近似重复。

---

## 50. 硬性检查

阻断交付：

- YAML 无法解析；
- ID 重复；
- QA 缺题面或答案；
- Cloze 无效；
- 无 Source；
- 核心操作完全没有覆盖；
- 重要参数缺失；
- 高风险错误结论；
- 明显重复；
- 代码块损坏；
- HTML 预览失败；
- 章节标签仍指向已废弃旧架构；
- 背景导致题面存在多个正确答案；
- 题面一次考多个独立目标。

---

## 51. 非阻断提醒

- 某专题卡片异常少；
- 参数卡比例过低；
- 输出卡比例过低；
- 题面背景过长；
- Extra 过长；
- Cloze 比例过高；
- P0 比例过高；
- 多行代码只集中在少数章节；
- 同类命令只出现模块名，没有字段或任务骨架；
- 综合任务只有方法论卡，没有具体任务。

# 第十六部分　从讲义生成 Anki 的流程

## 52. 单专题制卡流程

### 第一步：读取专题结构

提取：

```text
专题本质
知识节点
操作节点
参数节点
验证节点
诊断节点
边界
Cheatsheet
经典任务
```

### 第二步：标记原子提取目标

每个点判断：

- 是否需要记忆；
- 是否能独立作答；
- 是否有明确对错；
- 是否适合 QA；
- 是否适合 Cloze；
- 是否需要背景；
- 是否已有重复卡。

### 第三步：建立卡片家族

对 P0 操作考虑：

```text
对象
语义
命令
参数
任务
输出
验证
诊断
边界
```

不机械全建，只建立有独立价值的方向。

### 第四步：补充讲义外卡片

讲义外可增加：

- man page 高频参数；
- 典型命令组合；
- 真实输出字段；
- 工作中常见变式；
- 帮助入口；
- RHCE Collection/FQCN；
- 版本敏感内容。

标记：

```text
coverage::extra
```

### 第五步：调整题面背景

- 命令/参数：轻量；
- 验证/诊断：中等；
- 流程/综合：较完整。

### 第六步：检查答案

- 最低答案是否一眼可见；
- Extra 是否过长；
- 代码是否真实；
- 是否泄露答案；
- 是否与讲义一致。

### 第七步：覆盖与重复检查

运行自动检查和人工抽查。

# 第十九部分　最终自检清单

## 54. 内容价值

- 这张卡是否帮助操作、判断、验证或排错？
- 是否只是“文科式”背诵？

- 是否有明确答案边界？

- 对象是否明确？
- 当前状态是否足够？
- 目标是否明确？
- 背景是否适量？
- 是否排除关键歧义？
- 是否泄露答案？
- 是否只考一个主要目标？

## 56. 答案

- 最低答案是否一眼可见？
- 是否精确？
- 是否过长？
- 代码是否可复制？
- 补充是否只解决当前疑问？
- 是否误把局部状态写成整体成功？

## 57. 深度

- 核心操作是否只有一张卡？
- 是否覆盖关键参数？
- 是否有具体任务卡？
- 是否有输出判断？
- 是否有验证边界？
- 是否有诊断下一步？
- 是否有安全边界？

## 58. 维护

- ID 是否唯一稳定？
- Source 是否存在？
- 标签是否正确？
- 是否存在旧章节标签？
- 是否与其他卡实质重复？
- 优先级是否合理？
- 讲义外内容是否标记 `coverage::extra`？

# 第二十部分　最终原则

整套 Anki 应遵循：

> 卡片不是章节摘要。  
> 深度来自多角度提取，而不是长答案。  
> 题面需要适量背景，但背景不能替代答案。  
> 命令卡和参数卡使用轻量背景。  
> 输出卡、验证卡和诊断卡使用中等背景。  
> 流程卡和综合任务卡使用较完整背景。  
> 一个高价值操作应形成卡片家族。  
> 每张卡只训练一个主要提取目标。  
> 卡片数量由知识树决定，不按章节配额。  
> 当前状态、持久状态和功能状态必须分别训练。  
> RHCSA 训练手工系统状态，RHCE 训练自动化表达。  
> YAML 是内容真相，APKG 和 Anki Note 是构建产物。  
> 稳定 ID 代表提取目标，背景优化通常不改变 ID。  
> 最终卡片应帮助读者在真实终端中快速决定：下一步做什么、为什么做、如何证明。
