# 红帽 RHCSA / RHCE 讲义撰写规范

## 1. 文档定位

这套讲义面向 RHEL 9 RHCSA 与 RHCE 实操考试。它不是教材摘要、命令手册、模拟题答案合集，也不是为了出版效果而设计的“精装技术书”。它的任务是把官方能力范围、RH124/RH134/RH294 课程材料、模拟题中的任务形态和必要的官方资料，重新组织为一套适合连续阅读、主动记忆和考试操作的中文讲义。

讲义必须同时完成四件事：

1. 建立对象、状态和机制之间的正确关系；
2. 把知识转化为可执行的命令、配置或 Playbook；
3. 训练从题目、现象和输出中作出判断；
4. 为 Anki 卡片提供稳定、可追踪的知识与操作基础。

讲义正文以中文为主。命令、路径、模块名、配置字段、输出和重要英文术语保持原文。重要术语第一次出现时，可建立中英文对应，后续使用最符合考试环境的称呼。

## 2. 范围与基本约束

### 2.1 当前项目范围

当前项目只建设：

- RHCSA / RHCE 讲义 Markdown；
- 面向屏幕阅读的 PDF；
- 与章节对应的 Anki 卡片源和预览；
- 章节覆盖检查与静态质量检查。

暂不建设虚拟机、快照、自动评分、实验初始化或环境重置系统。讲义中的操作仍要做到逻辑闭环，但 Codex 必须假设自己始终无法访问真实虚拟机。

### 2.2 静态可信原则

所有命令、路径、参数和任务流程都通过课程材料、官方资料和逻辑推演进行静态核对。不能使用“已实测”“已跑通”等措辞。

资料发生冲突时采用以下优先级：

```text
RHEL 9 考试能力范围
→ Red Hat RHEL 9 课程材料
→ Red Hat / Ansible 官方文档
→ 课程实验和多份高可信资料的一致结论
→ 模拟题及其参考答案
```

无法确认的低价值细节不写。无法确认但可能影响核心任务的内容不能做成确定结论，也不能进入精确背诵型 Anki 卡。

### 2.3 正文不可见的维护信息

来源、验证状态、稳定 ID 和内部映射属于维护层。它们可以存在于 YAML Front Matter、HTML 属性或 HTML 注释中，但不得渲染到 Markdown 预览或最终 PDF。

正式讲义中不显示逐章“版本说明”“静态验证说明”“来源说明”。整套材料如需说明编写边界，只在全书前言统一出现一次。

## 3. 整体内容结构

整套内容源统一维护，默认生成两本学习版 PDF：

```text
RHEL9-RHCSA-讲义.pdf
RHEL9-RHCE-讲义.pdf
```

需要时由同一内容源自动生成合订版，不维护第三份手工文档。

全书前部设置一个完整的考试方法章节，内部依次讲：

1. 通用实操方法；
2. RHCSA 的考试操作流程；
3. RHCE 的考试操作流程；
4. 两份一页以内的精简检查清单。

后续章节仍要在真实知识和操作中重复落实相关策略，例如“先查看当前状态”“区分当前生效与持久配置”“操作后立即验证”“RHCE 执行成功不等于远端终态正确”。

## 4. 章节结构

### 4.1 章首

每章从新页开始，只显示章节编号、章节标题和一段必要的简短引入。不要添加章节封面、背景图、艺术编号、空泛引语、大段学习目标或章节地图。

推荐形式：

```markdown
# 第八章　管理 LVM 逻辑存储

LVM 把底层磁盘容量组织成可分配、可扩展的逻辑块设备……
```

引入只需说明：

- 本章处理什么问题；
- 为什么这个问题容易出错；
- 本章最终要形成什么操作能力。

### 4.2 章首概念与操作语义

简短引入之后，先建立本章的最小认知地图。这里不是术语表，也不是命令清单，而是用自然语言把相关概念和主要操作串起来。

使用两种行内标记：

```markdown
**[概念]** 物理卷（Physical Volume，PV）、卷组（Volume Group，VG）与逻辑卷（Logical Volume，LV）构成 LVM 的三层容量对象……

**[操作语义]** `pvs`、`vgs`、`lvs` 分别读取 PV、VG、LV 元数据；`pvcreate`、`vgcreate`、`lvcreate` 才依次建立这三层对象。
```

要求：

- 相关概念可以在同一段中共同解释；
- 介绍概念时要说明其在系统和考试任务中的作用；
- 操作语义只回答“该命令本质上观察或改变什么”，保持短而准；
- 自然语言负责串起概念之间的关系；
- 不把章首写成几十条互不关联的列表；
- 后续专题使用新命令前，仍要在合适位置补足其操作语义和关键参数。

## 5. 专题体系

正式专题标题必须在行首标注类型：

```markdown
## [知识专题] 对象层级、容量单位与查询边界
## [操作专题] 从空闲设备建立 PV、VG 与 LV
## [诊断专题] 根据症状定位失败所在层
## [经典任务] 建立并扩展一个可持久挂载的项目卷
## [参考解答] 按对象依赖完成创建、挂载与扩容
## [本章收束] 把命令还原为对象变化
```

类型标记用于帮助定位，标题主体必须自然、明确、能够说明当前部分真正解决什么问题。

### 5.1 专题的内聚性

一个专题应当围绕一个中心问题或一个目标终态独立成立。读者从 PDF 书签直接进入专题时，不应依赖上一段省略的主语、状态或结论。

专题不能只是“接着上一段继续说”。每个专题至少要明确：

- 当前对象或问题是什么；
- 哪些知识点、操作点共同解决它；
- 操作或判断的边界在哪里；
- 最终怎样确认本专题已经闭环。

场景可以帮助理解，但不能主导专题结构。不能为了维持一个故事而减少知识和操作覆盖，也不能让大量篇幅消耗在故事推进上。专题的本质仍是对一组高关联知识点、操作点、验证点和诊断点的聚合。

### 5.2 专题内部组织

专题内部优先使用 `①②③` 这类圆圈数字组织若干高密度单元：

```markdown
### ① [知识点] 六层对象不能互相替代
### ② [知识点] PE、LE 与两种容量表达
### ③ [操作点] 用一组查询建立对象映射
```

可使用的点类型包括：

```text
[知识点]
[操作语义]
[操作点]
[参数点]
[验证点]
[诊断点]
[边界]
```

使用原则：

- 圆圈数字用于组织真正独立但强关联的内部单元；
- 一个点只聚合一组高度相关的信息；
- 自然语言用于解释关系、原因和记忆线索；
- 不能把每句话都拆成点，也不能在一个专题中无分隔地平铺十几个段落；
- 点标题应切中要害，不能写成“基本介绍”“操作步骤”“注意事项”。

### 5.3 自然语言的角色

自然语言负责：

- 解释为什么这些知识放在一起；
- 建立对象和状态之间的联系；
- 说明参数选择的依据；
- 帮助把命令记忆为对象变化；
- 从一个知识点平滑过渡到下一个知识点。

自然语言不负责制造低信息密度的场景叙述。正文应尽量做到一句话推进一个判断，不使用大量“然后、接着、之后、我们再来看”来填充结构。

## 6. 知识专题

知识专题以机制、关系和判断边界为中心，但不能成为纯理论章节。它通常需要把概念、命令查询入口、输出含义和考试判断组织在一起。

一个合格的知识专题通常包含：

- 一组对象及其关系；
- 容易混淆的边界；
- 至少一个用于观察该关系的命令或输出；
- 该知识如何改变读题或排错方式；
- 专题末的精炼 Cheatsheet。

知识讲解深度以“足以解释操作、帮助迁移和诊断高频失败”为准，不扩展到与考试无直接帮助的内部实现。

例如讲 LVM，不只给出 PV、VG、LV 的定义，还要讲清：

```text
设备存在 ≠ 可以安全初始化
LV 存在 ≠ 文件系统存在
目录存在 ≠ 已经挂载
当前挂载成功 ≠ 启动后仍会挂载
```

## 7. 操作专题

### 7.1 基本闭环

操作专题必须形成：

```text
目标或前提
→ 操作语义与关键参数
→ 代码或配置
→ 验证
→ 必要的错误边界
→ Cheatsheet
```

强制的是内容闭环，不是固定显示所有栏目。`[分析思路]`、`[验证]`、`[常见错误]` 等行内标签按需使用。

### 7.2 新指令的引入检查

专题使用任何重要命令之前，必须检查：

1. 该命令是否已在章首或前文说明过基本语义；
2. 当前使用的关键参数是否已经解释；
3. 读者是否能理解它作用于哪个对象；
4. 后续验证命令是否说明了自己能证明什么、不能证明什么。

若命令第一次出现，应在代码块之前用一小段话介绍：

- 命令本质上改变或查询什么；
- 本次最重要的 1～3 个参数；
- 参数选择与题目目标之间的关系。

不要把参数说明扩张成手册。

推荐：

> `lvcreate` 中最常用的三个参数是：`-n` 指定 LV 名称，`-l` 按 extent 数量或百分比分配，`-L` 按容量分配。题目按 extent 描述时，不要先换算成近似容量再使用 `-L`。

不推荐：

```text
-n：名称
-l：extent
-L：容量
-y：自动确认
-W：擦除签名
-Z：清零
……
```

### 7.3 代码块与行末注释

代码块中的关键条目可以使用对齐的行末注释，简要说明“这条命令在改变或证明什么”：

```bash
pvcreate /dev/vdb1                              # 初始化 PV
vgcreate -s 16M projectvg /dev/vdb1             # 创建指定 PE 的 VG
lvcreate -l 50 -n projectlv projectvg           # 创建 50 LE 的 LV
```

规则：

- 只给关键条目加注释，不要求每一行都有；
- 注释必须短，通常不超过一个动作或一个判断；
- 同一代码块中的注释尽量对齐；
- 不在注释中重新解释全部参数；
- 长命令由作者按 Shell 语法主动换行，不能依赖 PDF 自动折行；
- YAML、配置和 Jinja2 保持真实缩进，不使用行末注释破坏语义；
- 终端会话使用 `console`，可复制命令块不带 `$` 或 `#` 提示符。

### 7.4 验证

验证按任务选择必要层次，不机械套模板。可选层次包括：

```text
配置是否存在
对象当前状态是否正确
功能是否达到目标
外部访问是否成立
持久配置是否成立
RHCE 第二次执行是否保持幂等
```

验证命令必须说明它能证明什么。不能用“命令退出码为 0”代替系统终态。

例如：

```bash
lvs projectvg/projectlv -o lv_size,lv_path       # 证明 LV 层容量
df -hT /srv/project                              # 证明文件系统层容量
findmnt /srv/project                             # 证明当前挂载关系
```

### 7.5 常见错误

`[常见错误]` 只在存在典型、可迁移且会造成真实失分的错误模式时使用。每个专题通常只保留 1～3 个：

- 只改变当前状态，没有建立持久配置；
- 查询了错误对象；
- 局部状态正确，却误判整个任务完成；
- 参数的增量语义、目标语义或范围语义混淆；
- 破坏性命令被当成排错手段。

不要收集所有可能报错，也不要把拼写错误写成专题。

### 7.6 专题末 Cheatsheet

知识专题、操作专题和诊断专题结束时，原则上提供一条非常精炼的 Cheatsheet。它不是新的命令手册，而是把前面已经解释过的内容重新压缩为可调用的操作骨架。

推荐：

> **[Cheatsheet]** 查余量：`vgs ... vg_free_count`；直接扩容：`lvextend -l +N -r <VG/LV>`；空间不足：`pvcreate <DEV>` → `vgextend <VG> <PV>` → 再扩容；验收：`lvs` + `df` + `findmnt` + 数据校验。

要求：

- 只出现已经在专题中解释过的命令和概念；
- 通常 1～4 行；
- 切中命令选择、操作顺序和验证边界；
- 不写长句，不引入新知识；
- 不把所有参数重新罗列一遍。

## 8. 诊断专题

诊断专题训练：

```text
现象
→ 当前状态
→ 假设
→ 证据
→ 下一步动作
```

它不追求穷举错误，而是选择高频、代表性症状，帮助读者判断失败位于哪一层。

例如 LVM：

- `lvs` 增长而 `df` 不变：文件系统层未扩展；
- 目录存在而 `findmnt` 无结果：当前未挂载；
- `lvextend` 空间不足：先查 VG 余量；
- 候选设备已有签名或归属：停止破坏性操作。

诊断专题可以包含一张简洁的“证据推进图”，但图只表达主要判断路径，不画成包含所有异常分支的巨大决策树。

## 9. 经典任务

每章至少包含一个能够串联主要能力的经典任务，或若干足以覆盖主线的中型任务。

### 9.1 任务页

任务页只包含：

- 初始状态；
- 目标终态；
- 限制条件；
- 验收要求。

不得直接给出命令、专题名称或解题顺序。跨度较大的任务可以在页末提供 2～3 个弱化的“卡住时再想一想”问题，但不能泄露答案。

任务页结束后强制分页。

### 9.2 参考解答

参考解答从下一页开始，按照：

```text
读题与对象拆解
→ 当前状态调查
→ 稳定操作路径
→ 分层验证
→ 1～3 个高价值错误边界
→ 精炼 Cheatsheet
```

完整解答只提供一条稳定、推荐的路径。其他方案只有在适用条件实质不同且具有考试价值时才说明。

错误路径只能短暂穿插，用于解释证据不足、持久性差异或安全边界，不能喧宾夺主。

## 10. Anki 与讲义的边界

讲义必须自包含地讲清考试核心机制和主要操作，不能把重要解释推给 Anki。

Anki 可以比讲义更“极客”、更细、更全面，尤其覆盖：

- 命令骨架；
- 关键参数；
- 高频参数组合；
- 命令与对象的映射；
- 典型输出；
- 任务变式；
- 验证命令；
- 诊断下一步；
- 帮助和查询入口。

讲义中不必为每个低频参数腾出版面，但专题使用到的重要命令和关键参数必须先在讲义中解释。Anki 不能成为首次引入完整重要机制的地方。

## 11. 写作与排版风格

### 11.1 信息密度

正文需要自然、可读，但不能低密度。判断一段话是否应保留：

- 是否建立了新的关系；
- 是否解释了参数选择；
- 是否帮助读题、操作、验证或排错；
- 是否提供了记忆线索；
- 是否只是重复场景和过渡。

不能因为“自然语言组织”而写成长篇场景叙述。自然语言应当把知识点和操作点对齐，而不是掩盖它们。

### 11.2 列表与表格

- 机制、原因和判断优先写成自然段；
- 真正并列的信息可以使用短列表；
- 横向比较才使用表格；
- 不把普通段落强行拆成条目；
- 不在表格单元格中塞长段解释。

### 11.3 重点

- 命令、路径、配置项和输出使用行内代码；
- 加粗只用于关键判断、否定边界或核心对象；
- 一段通常只强调一个短语；
- 不整句、整段加粗；
- 不使用大量彩色文字、图标和徽标。

### 11.4 提示框

只保留两类：

```text
关键提醒
环境说明
```

普通技巧、验证、常见错误和补充知识回到专题正文。页面不连续堆放提示框。

### 11.5 图与截图

图只用于：

- 层级关系；
- 拓扑关系；
- 状态路径；
- 诊断分支；
- 作用边界。

截图只用于真实界面识别。命令、YAML、日志和输出必须保持为可复制文本。

## 12. PDF 规范

- A4 纵向，面向电脑屏幕优化；
- 正文行距舒展，代码字体略小但可读；
- 新章从新页开始；
- 不设置复杂章首；
- 不设置页眉；
- 页脚只显示低调页码；
- 纸面目录主要显示篇章与章节；
- PDF 书签覆盖知识专题、操作专题、诊断专题和经典任务；
- `[知识点]`、`[操作点]`、`[验证点]` 等内部点标题不进入目录；
- 稳定 ID 作为隐藏 HTML 锚点，不显示在标题、页眉或页脚；
- 代码排版不得改变语义；
- 经典任务题目与答案强制分页。

构建链路固定为：

```text
Markdown
→ 规范化 HTML
→ 集中式 CSS
→ 固定 HTML/CSS PDF 渲染器
```

所有章节共用模板和 CSS，不能每章单独设计样式。

## 13. 来源、ID 与目录结构

推荐章节目录：

```text
content/
```

## 14. 章节完成条件

一个章节只有同时满足以下条件才算完成：

1. 章首概念与操作语义已建立；
2. 专题数量克制，但每个专题足够内聚；
3. 知识点、操作点、验证点和诊断点被清晰呈现；
4. 重要命令在使用前已介绍基本语义和关键参数；
5. 关键代码行有简短、必要的行末注释；
6. 每个专题有可调用的精炼 Cheatsheet；
7. 至少一个经典任务覆盖主要能力；
8. 参考解答具备完整操作与验证闭环；
9. 没有可见版本说明、来源和内部 ID；
10. 对应 Anki YAML 已生成并通过覆盖检查；
11. PDF 和 Anki HTML 预览成功生成；
12. 没有把未经确认的内容写成确定结论。

## 15. 编写自检清单

### 章节级

- 本章是否解决一个明确领域问题？
- 章首概念是否自然串联，而非术语堆积？
- 专题是否能够独立阅读？
- 是否存在“接着上一段继续说”才能理解的专题？
- 场景是否帮助理解，而没有牺牲信息密度？
- 是否覆盖核心操作、验证和诊断？
- 是否有完整经典任务？

### 专题级

- 标题是否标明 `[知识专题]`、`[操作专题]` 或 `[诊断专题]`？
- 内部是否用 `①②③` 组织了真正的知识点和操作点？
- 每个新命令是否介绍了语义？
- 重要参数是否在代码前解释？
- 行末注释是否短、准、对齐且不过量？
- 验证命令是否说明了证明边界？
- Cheatsheet 是否只压缩已讲内容？

### 文字级

- 是否一句话推进一个判断？
- 是否存在无价值的场景叙述或过渡？
- 是否大段加粗或过度使用列表？
- 是否把命令成功误写为任务成功？
- 是否把当前状态误写为持久状态？
- 是否使用“实测”“已跑通”等不准确表述？
# 阅读版 PDF 语义合同

正式 PDF 遵循 [PDF 大字号阅读版排版规范](PDF大字号阅读版排版规范.md)。渲染器只消费源中显式概念组件，将其确定性归一化为全宽单列概念块：名词加粗换色，作者的完整自然解释保持原样；不得拆句、生成解释或注入机械标签。显式操作速查先写作用对象、改变和边界，关键入口具有 SYNOPSIS，重要参数逐项换行。禁止双列概念、可见页眉页脚页码；导航依靠可点击目录和分层书签。
