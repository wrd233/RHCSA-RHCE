## 6. 讲义写作要求

## 6.1 章首

每章从新页开始，只显示：

- 章节编号；
- 章节标题；
- 一段简短引入。

不要添加：

- 独立章节封面；
- 装饰图；
- 大号艺术编号；
- 空泛引语；
- 大段学习目标；
- 可见版本说明；
- 可见来源说明。

## 6.2 章首概念与操作语义

每章开头必须用自然语言建立概念和操作地图。

使用：

```markdown
**[概念]** 概念中文（English，缩写）：简短而准确的介绍。

**[操作语义]** `command`：本质上查询或改变什么。
```

要求：

- 相关概念可在一个段落中自然串联；
- 不写成孤立术语表；
- 不写成命令清单；
- 操作语义简短，只回答本质作用；
- 重要命令在后续首次正式使用前，仍需补充关键参数说明。

## 6.3 专题标题

正式专题标题必须标注：

```markdown
## [知识专题] ...
## [操作专题] ...
## [诊断专题] ...
## [经典任务] ...
## [参考解答] ...
## [本章收束] ...
```

专题必须能够独立阅读。不能依赖“接着上一段”才能理解。

## 6.4 专题内部

优先使用：

```markdown
### ① [知识点] ...
### ② [操作点] ...
### ③ [验证点] ...
```

可用类型：

```text
[知识点]
[操作语义]
[操作点]
[参数点]
[验证点]
[诊断点]
[边界]
```

要求：

- 每个专题只聚合一组高关联知识和操作；
- 自然语言负责解释关系和帮助记忆；
- 场景只服务理解，不能牺牲信息密度；
- 不能写成低密度故事；
- 不能把所有内容平铺为连续段落；
- 不能把每句话都拆成条目。

## 6.5 新命令与参数

任何重要命令首次出现前，都要检查：

1. 是否已经说明基本语义；
2. 当前关键参数是否已经解释；
3. 读者是否知道它作用于什么对象；
4. 后续验证能证明什么。

代码块前只介绍最重要的 1～3 个参数，不写参数大全。

示例：

> `lvcreate` 中，`-n` 指定 LV 名称，`-l` 按 extent 数量或百分比分配，`-L` 按容量分配。题目按 extent 描述时，应直接使用 `-l`。

## 6.6 代码块

关键条目使用简短、对齐的行末注释：

```bash
pvcreate /dev/vdb1                              # 初始化 PV
vgcreate -s 16M projectvg /dev/vdb1             # 创建指定 PE 的 VG
lvcreate -l 50 -n projectlv projectvg           # 创建 50 LE 的 LV
```

规则：

- 只注释关键条目；
- 注释短、准、对齐；
- 不在注释中重复参数说明；
- 命令由作者按 Shell 语法主动换行；
- YAML 和 Jinja2 保持真实缩进；
- 可复制命令块不带提示符；
- 展示输入输出的会话使用 `console`。

## 6.7 验证

操作专题必须形成目标、操作和验证闭环。

验证应按任务选择必要层次：

```text
配置
→ 当前状态
→ 功能
→ 外部访问
→ 持久性
→ RHCE 幂等性
```

每个验证命令要说明：

- 它能证明什么；
- 它不能证明什么；
- 是否还需要另一层验证。

不能把命令退出码为 0 当成整个任务完成。

## 6.8 常见错误

只保留 1～3 个典型、可迁移并容易造成失分的错误：

- 只改变当前状态；
- 没有持久化；
- 查询错误对象；
- 局部正确但误判整体完成；
- 增量值与目标值混淆；
- 破坏性命令被当作排错手段。

不要整理报错大全。

## 6.9 Cheatsheet

每个知识专题、操作专题和诊断专题结束时，提供非常精炼的 Cheatsheet。

示例：

> **[Cheatsheet]** 查余量：`vgs ... vg_free_count`；扩容：`lvextend -l +N -r <VG/LV>`；空间不足：`pvcreate` → `vgextend` → 再扩容；验收：`lvs` + `df` + `findmnt`。

要求：

- 只压缩已经解释过的内容；
- 不引入新知识；
- 通常 1～4 行；
- 重点是命令选择、操作顺序和验证边界；
- 不能扩张成命令手册。

## 6.10 经典任务

每章至少一个综合经典任务。

任务页包含：

- 初始状态；
- 目标终态；
- 限制条件；
- 验收要求。

任务页不得泄露命令和专题名称。跨度较大时，可提供 2～3 个弱化的“卡住时再想一想”。

题目后强制分页。

参考解答包含：

```text
读题拆解
→ 当前状态调查
→ 推荐路径
→ 分层验证
→ 少量错误边界
→ Cheatsheet
```

只提供一条稳定推荐路径。

## 6.11 文字风格

- 中文自然、可读；
- 一句话尽量推进一个判断；
- 信息密度高；
- 不写大段场景叙述；
- 不写教材式空泛过渡；
- 不大段加粗；
- 命令、路径、参数和输出使用行内代码；
- 列表只用于真正并列的信息；
- 表格只用于必要横向比较；
- 图只用于层级、拓扑、状态路径和诊断分支；
- 截图只用于真实界面识别。

## 7. Anki 要求

## 7.1 定位

Anki 必须比讲义更“极客”、更深入地覆盖：

- 命令骨架；
- 参数语义；
- 典型参数组合；
- 任务变式；
- 输出判断；
- 验证命令；
- 故障下一步；
- 配置路径；
- Ansible 模块、字段和结构；
- 帮助和查询入口。

减少“文科式”卡片：

- 不要求背长篇定义；
- 不制作开放性作文题；
- 不逐段概括讲义；
- 不为了覆盖率机械转卡。

## 7.2 覆盖

每个具有独立考试价值的：

```text
知识关系
操作点
参数点
验证点
诊断点
经典任务关键步骤
```

至少有一种主动提取表达。

高价值内容可分别制作：

```text
目的 → 命令
命令 → 作用
参数 → 语义
输出 → 判断
现象 → 下一步
任务 → 流程
错误 → 风险边界
```

这些是不同提取路径，不属于重复。

## 7.3 Note Type

只保留：

```text
RedHat-QA
RedHat-Cloze
```

每章一个 `anki.yml`，字段固定：

```text
id
type
question / answer
或 text
extra
source
tags
disabled（可选）
```

## 7.4 卡片结构

正面：

- 最小充分上下文；
- 一个提取目标；
- 必要的命令、输出或代码。

背面：

- 不重复题面；
- 先显示最低合格答案；
- 再显示必要的短补充；
- 不显示章节、来源、ID、标签、卡片类型。

答案要：

- 精炼；
- 清楚；
- 可读；
- 一眼可判断；
- 不整段加粗；
- 不堆视觉元素。

## 7.5 颗粒度

- 原子卡为主；
- 少量流程骨架卡；
- 一张 QA 卡只训练一个目标；
- 一个 QA YAML 条目生成一张卡；
- Cloze 通常只有 1 个编号，最多 2 个紧密相关编号；
- 不挖长命令或整段 Playbook；
- 输入型只用于短、精确、容易拼错的答案。

## 7.6 标签

每张普通卡至少包含：

```text
exam::rhcsa 或 exam::rhce
chapter::<chapter>
card::<type>
```

按需增加：

```text
priority::P0
priority::P1
coverage::extra
topic::<topic>
task::<task>
version::sensitive
origin::mistake
bridge::rhce
```

来源只保存在 `source` 字段。

## 7.7 ID 与更新

稳定 ID 代表主要提取目标。

- 措辞和排版变化保留 ID；
- 提取方向或核心能力变化创建新 ID；
- 不再使用的卡只增加 `disabled: true`；
- 不自动永久删除。

## 7.8 Anki 预览与同步

每章生成：

```text
anki.yml
anki-preview.html
anki-summary.md
```

HTML 使用最终卡片模板显示正面和背面。

**本 Goal 中不要自动调用 AnkiConnect 同步到我的现有 Anki。**

完成后我会先查看 PDF 和 Anki 预览。只有我之后明确要求同步时，才调用 AnkiConnect。

## 7.9 `.apkg`

完成全部章节后生成：

- RHCSA `.apkg`
- RHCE `.apkg`

需要时可额外生成合并牌组 `.apkg`。

`.apkg` 用于备份和迁移，不替代 YAML 内容源。

## 10. 自动检查

## 10.1 讲义硬性检查

至少检查：

- 每章存在章首概念与操作语义；
- 正式专题标题有类型标记；
- 稳定 ID 唯一；
- 无可见版本说明、来源和内部 ID；
- 操作专题包含操作与验证；
- 新命令在使用前有语义说明；
- 关键参数有介绍；
- 关键代码行有简短注释；
- 专题末有 Cheatsheet；
- 经典任务有任务页、分页和参考解答；
- 代码块和 HTML 结构完整；
- PDF 可成功渲染；
- PDF 书签和页码正常。

## 10.2 Anki 硬性检查

至少检查：

- YAML 可解析；
- ID 唯一；
- QA 题面和答案存在；
- Cloze 合法；
- 标签包含考试、章节和类型；
- 重要操作、参数、验证和诊断不存在核心覆盖缺口；
- 无明显重复卡；
- 无高风险不确定结论；
- HTML 预览可生成；
- `.apkg` 可构建。

## 10.3 内容层检查

你还必须主动判断：

- 专题是否足够内聚；
- 是否存在依赖上一段才能理解的专题；
- 是否为了场景牺牲信息密度；
- 是否存在平铺直叙、低密度段落；
- 是否遗漏命令语义或关键参数；
- 是否把局部状态当成整体完成；
- 是否把当前状态当成持久配置；
- Anki 是否过于“文科式”；
- Anki 是否深入覆盖了典型命令、参数和任务；
- Cheatsheet 是否真正切中要害。

- 给每章单独设计 CSS；
- 在讲义中显示来源、版本、稳定 ID；
- 创建大量 Note Type；
- 让卡片背长篇定义；
- 自动生成所有反向卡；
- 自动同步到现有 Anki；
- 创建数据库、Web 后台或复杂工作流；
- 声称虚拟机实测；
- 因无法实测而停止完成操作内容。
